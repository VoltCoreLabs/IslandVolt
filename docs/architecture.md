# Архитектура

## Подход

Модульный монолит в Rust workspace. GPUI отвечает за представление; логика и интеграции
остаются независимыми. Это позволяет добавлять функции без разрастания главного окна.
На первом этапе не нужны микросервисы, динамическая загрузка кода и отдельный процесс на фичу.
В прототипе активны `app`, `platform-windows` и `features`; остальные пакеты остаются каркасом.
Первый независимый модуль `features::pets` содержит проверяемый формат пакета и проигрыватель;
GPUI entity и владение таймерами находятся в приложении.

## Слои и направление зависимостей

```text
app (composition root)
 ├─ ui ────────────────────> features ──> core
 ├─ platform-windows ──────────────────> core
 ├─ storage ───────────────────────────> core
 └─ providers ─────────────────────────> core
```

Стрелка означает зависимость исходного кода. `app` собирает реализации портов и передаёт их
фичам. Вызовы фич в сторону ОС идут через порты, поэтому обратная зависимость не нужна.
GPUI допустим в `app` и `ui`; остальные слои не должны импортировать GPUI.

| Пакет | Ответственность |
| --- | --- |
| `islandvolt-app` | Запуск, завершение, жизненный цикл, связывание зависимостей |
| `islandvolt-core` | Идентификаторы, ошибки, команды/события, порты, capabilities |
| `islandvolt-features` | Независимые доменные модули и сценарии пользователя |
| `islandvolt-ui` | Оболочка GPUI, карточки, темы, доступность, анимации |
| `islandvolt-platform-windows` | Нативные API и владение Windows-ресурсами |
| `islandvolt-storage` | Репозитории, настройки, миграции, доступ к секретам |
| `islandvolt-providers` | Адаптеры локальных моделей и сетевых сервисов |

Создан только пакет приложения; остальные пакеты пока запланированы. Отдельный feature-crate выделяется,
когда появляются тяжёлые зависимости, отдельные требования сборки или независимый жизненный цикл.

## Контракт фичи

Каждая фича описывает:

- Уникальный ID, название, доступность и зависимости от capabilities.
- Типизированные команды, события и состояние для отображения.
- Необходимые разрешения и ожидаемые внешние ошибки.
- Запуск, приостановку и остановку с отменой фоновых задач.
- Восстановление после исчезновения устройства, отключения сети или сна системы.

Карточка фичи находится в `ui/cards/<feature>` и читает подготовленную модель отображения.
Внешние адаптеры возвращают доменные типы, а не COM-указатели и структуры GPUI.
Общие контракты хранятся в тематических подмодулях core, а не в одном большом файле.

## Поток данных

```text
Windows event → adapter → typed domain event → feature state
                                              ↓
                                     presentation snapshot → GPUI
GPUI action → typed command → permission check → feature → port → adapter
```

UI не выполняет побочных эффектов при рендеринге. У каждого состояния есть один владелец.
Частые события громкости/прогресса объединяются; снимок содержит актуальное значение.
Для команд с результатом используются request ID, ответ и явное состояние выполнения.

## Планирование задач

- GPUI-поток: ввод, лёгкие переходы состояния, построение представления.
- Windows-workers: COM/WinRT с корректной apartment-моделью и потоком освобождения.
- Фоновые I/O-задачи: сеть, БД, файлы; используемый runtime выбирается на этапе 0.
- Ограниченный пул тяжёлых задач: OCR, ASR, распознавание, кодирование.
- Аудио/видео: отдельный ограниченный конвейер буферов, без передачи кадров через UI-события.

Не запускать второй async-runtime автоматически: сначала проверить модель исполнения GPUI.
У каждого задания есть cancellation token, лимит ресурсов, таймаут, политика ошибки.
Переполнение не должно тихо терять команды: отказ сообщается вызывающему коду.
Допустимо объединять телеметрию; жизненный цикл записи и запросы разрешений не отбрасываются.

## Ресурсы и завершение

При выключении фичи: отменить задачи → отписаться → закрыть устройства → сохранить состояние.
При выходе приложения: запретить новые задачи → корректно завершить запись → закрыть фичи
→ сбросить хранилище → освободить нативные ресурсы → закрыть окно.
Завершение ограничено временем; незакрытая запись получает восстанавливаемый статус.

## Расширяемость

Встроенный реестр фич управляет доступностью и UI-вкладом, но не становится универсальной шиной всего.
Контракты capability имеют состояния `available`, `unavailable`, `permission_required`, `degraded`.
Фича с отсутствующей capability предлагает объяснение и доступный fallback.
Новые ИИ/ASR/погодные провайдеры реализуют существующий порт.
Изоляция тяжёлых моделей в отдельный процесс рассматривается при измеренной необходимости.

## Проверки архитектуры

- Доменные тесты: состояние, приоритеты, таймеры с подменяемыми часами.
- Контрактные тесты: адаптеры и провайдеры соблюдают одинаковую семантику.
- Интеграционные проверки: настоящий Windows API, БД и отмена задач.
- UI: фокус, переходы, DPI, состояние ошибки, доступность с клавиатуры.
- Производительность: простой, музыка, анимация, нагрузка, скрытие и батарея.
